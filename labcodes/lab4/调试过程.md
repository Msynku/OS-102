# lab4 调试过程记录

> 记录 lab4 中最棘手的一个 bug（`check_boot_pgdir` 的 store page fault）的完整排查过程与调试文档说明。

## 一、现象复现

编译运行后 `check_alloc_page()`、`check_pgdir()` 均通过，但内核在 `check_boot_pgdir()` 的 `strcpy((void *)0x100, "ucore: Hello world!!")` 处卡死，控制台反复刷 `DTB Init`，随后第二次启动时 panic `pa2page called with invalid pa`。

## 二、先抓 qemu 的 MMU 日志

用 `qemu -d mmu,guest_errors -D log` 运行，抓到关键一行：

```
riscv_cpu_tlb_fill ad 100 rw 1 mmu_idx 1
riscv_cpu_tlb_fill address=100 ret 1 physical 0000000000000000 prot 0
```

`rw 1` 表示一次写访问，`ret 1` 表示页表遍历失败（TRANSLATE_FAIL），于是把问题锁定在"硬件对 0x100 的地址翻译"上。

## 三、在 check_boot_pgdir 里插桩，读软件视角的页表

加入 DBG 打印，打印 root[0]、level1[0]、leaf 三级页表项和 satp：

```
root[0]   = 0x20104811  →  一级表 0x80412000
level1[0] = 0x20104c11  →  二级表 0x80413000
leaf[0]   = 0x201044c7  →  物理页 0x80411000（V|R|W|A|D，可写）
satp      = 0x800000000008020b
```

从软件角度，三级页表项"完全正确"：V 位、可写位、物理页号都对，satp 也指向正确的根页表。

## 四、用 gdb 单步 + 直读物理内存，排除"页表内容写错"

gdb 断到 `strcpy`，单步确认故障点就是 `sb a4, 0(a5)`（写 0x100）这条指令；同时用 qemu 的 `monitor xp` 直接读物理内存 0x8020b000 / 0x80412000 / 0x80413000，读到的 PTE 值与软件读到的完全一致。说明**不是页表内容写错，而是硬件遍历规则上出了问题**。

## 五、顺藤摸瓜查 stvec，解释"重启"现象

gdb 里看到 `stvec = 0x80200000`（正好是 `kern_entry` 的地址），所以一旦 fault，CPU 就跳回内核入口重新启动——这就是日志反复刷 `DTB Init` 的原因。

## 六、逐项排除常见怀疑

- 给 inner PTE 补 A 位、补 A|D 位——无效；
- U 位一致性、satp 编码、`sfence.vma` 编码——逐一核对都正常。

## 七、查 qemu 源码定位根因

最终查到现代 qemu（自 commit `qemu/qemu@8fcfe17` 起）严格执行 RISC-V 规范：**非叶子（inner）页表项的 D/A/U 三个保留位必须全为 0**，否则直接返回 TRANSLATE_FAIL。而框架 `get_pte()` 创建中间级页表项时用了 `pte_create(ppn, PTE_U | PTE_V)`，把 U 位置成了 1——软件读起来"对"，硬件按规范解释却是"非法"。

## 八、修复与验证

把 `get_pte()` 两处 inner PTE 改为 `pte_create(ppn, 0)`，并把 `check_pgdir()` 里旧约定断言 `assert(boot_pgdir_va[0] & PTE_U)` 改为 `assert(!(boot_pgdir_va[0] & PTE_U))`。重新编译后 `check_boot_pgdir()` 通过，`initproc` 正常输出 "Hello world!!"。

## 九、调试工具小结

| 工具 | 用途 |
|---|---|
| `qemu -d mmu,guest_errors -D log` | 看每次 TLB 填充的成败（ret 0/1） |
| `qemu -S -s` + `riscv-none-elf-gdb` | 断点、单步、看寄存器（satp/stvec/pc） |
| gdb 里 `monitor xp` | 直读物理内存，绕过 MMU 核对页表真实内容 |
| gdb 里 `monitor info mem` | 看 TLB 当前缓存条目 |

## 十、调试文档说明

排查过程中产出并使用了以下几类调试文档/日志：

- **qemu MMU 日志**（`-d mmu,guest_errors -D log`）：记录每一次 TLB 填充请求的地址、读写属性、`mmu_idx` 以及结果（`ret 0` 成功 / `ret 1` 失败）。它是判断"到底是哪次地址翻译失败"的第一手证据。
- **gdb 断点/单步脚本**：用于断到 `strcpy`/`check_boot_pgdir` 并逐步定位到具体的故障指令 `sb a4, 0(a5)`。
- **物理内存 dump**（gdb 内 `monitor xp`）：绕过 MMU 直接读物理地址，用来核对页表"实际落盘"的内容与软件读到的是否一致。
- **寄存器快照**（satp / stvec / sstatus / pc）：确认根页表指针正确、并解释故障后为何跳回 `kern_entry` 重启。

这些文档的核心作用是**对照"软件视角"与"硬件视角"**：当软件读页表数值正确、硬件遍历却报失败时，先用物理内存 dump 排除"内容写错"，再结合 qemu 日志和源码定位到"规范解释差异"。上述中间日志/脚本在排查结束后已从 lab4 目录清理，本文档只保留结论性的定位步骤。

## 十一、教训

这个 bug 的迷惑性在于"软件读页表数值正确 ≠ 硬件翻译合法"。遇到"看起来都对但就是 fault"的情况，要相信硬件的判决，去查 ISA 规范或模拟器源码，而不是只盯着自己代码的逻辑正确性。另外本次还踩了一个环境坑：这版 qemu 上 `-device loader` 不设置启动地址（Next Address 变成 0），必须改用 `-kernel` 才能正常启动内核。
